# Preview Tool CLI — Product & Architecture Design

**Date:** 2026-02-27
**Status:** Draft
**Consumer:** PMs (spec authoring), designers (review), developers (integration)

---

## Problem

The current preview-tool generates UI screens, but the process requires:

1. **Technical knowledge** — screens are hand-coded in React/TypeScript
2. **Manual orchestration** — Claude Code skills (screen-spec, generate-screen) must be invoked separately with domain knowledge
3. **No portability** — the tool is a standalone project, not installable into other repos
4. **No typed output** — generated screens have no exported data interfaces for backend teams

The market has no tool that generates **multi-state, typed, tested UI screens** from plain English. Tools like v0, Bolt, and Lovable generate single happy-path states with dead buttons, hallucinated components, and no test coverage.

## Vision

A CLI tool that non-technical users can run in any React+Vite repo:

```
$ npx preview-tool init     # scaffold tokens, components, config
$ npx preview-tool add      # plain English → follow-ups → screen.yaml → all artifacts
$ npx preview-tool dev      # launch preview with dev tools
$ npx preview-tool export   # extract TypeScript interfaces
```

**Input:** plain English + structured follow-ups
**Output:** production-ready screen with scenarios, flows, tests, types, and translations

---

## Design Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| LLM engine | Claude Code (skills) | No separate API key; user already has Claude Code installed |
| Component model | Ship default L2 library | Consistent output quality; users extend/override |
| Output target | Into user's existing app | Screens integrate with their router; preview UI as dev tool |
| Spec format | YAML (screen.yaml) | Fully parseable for deterministic generation; PM-editable |
| Dev tools delivery | `@preview-tool/devtools` npm package | Embeddable via Vite plugin; dev dependency only |
| Screen discovery | Vite virtual modules | `import.meta.glob` is compile-time; plugin bridges the gap |
| Test generation | One test per region x state | Deterministic from spec; no LLM needed |
| i18n | Co-located en.json + de.json | Verbatim copy from spec; auto-discovered by runtime |

## The Spec Format: `screen.yaml`

### Why YAML

| Criterion | YAML | Markdown | JSON |
|-----------|:----:|:--------:|:----:|
| PM-readable | Yes | Yes | No |
| Deterministically parseable | Yes | Partial | Yes |
| Git-diffable | Yes | Yes | Noisy |
| Supports embedded types | Yes | Awkward | No |
| Familiar to non-devs | Moderate | High | Low |

YAML wins because the tool generates it (PM reviews, not writes) and it must be deterministically parseable. Markdown's free-form nature requires LLM interpretation for parsing.

### Schema

```yaml
# ── Meta ────────────────────────────
screen: {section}/{screen}        # route path
title: Screen Title               # human label
layout: list-with-header          # layout pattern key
section: {section}                # grouping in catalog

# ── Navigation ──────────────────────
flow:
  name: Flow Name                 # optional, standalone if omitted
  step: N of M                    # optional
  prev: /route                    # back target
  next: /route                    # forward target
  back: /route                    # explicit back button target

# ── Data Contract ───────────────────
data:
  {field}: {type}                 # string, number, boolean, date
  {field}: {A} | {B} | {C}       # union/enum
  {field}:
    type: list
    min_items: {N}                # >=10 for lists, >=100 for tables
    default_count: {N}            # inspector default (3 for lists, 10 for tables)
    item:
      {field}: {type}
      {field}: {type}
  {field}?: {type}                # optional field

# ── Regions & States ────────────────
regions:
  {region_name}:
    label: Region Label
    default: {state_key}
    states:
      {state_key}:
        {field}: {value}
        {list_field}: []           # empty for loading/empty states
      {state_key}:
        {field}: {value}
        {list_field}: $mock        # references generated mock data

# ── Elements ────────────────────────
elements:
  - ScreenHeader:
      title: $t({key})
      back: true | false

  - {ComponentName}({variant}):
      prop: value
      prop: $t({key})              # i18n reference
      prop: $data({field})         # data binding

  - when({field} == {value}):       # conditional section
      - {ComponentName}:
            prop: value

  - each($data({list_field}) as {item}):  # list iteration
      - {ComponentName}:
            prop: ${item}({field})

  - Footer:
      - Button({variant}, {modifier}):
          label: $t({key})
          disabled: when({condition})

# ── Flow Actions ────────────────────
actions:
  - trigger: {ComponentType}:$t({key})
    navigate: /route
  - trigger: {ComponentType}:$t({key})
    setState: {state_key}

# ── Strings ─────────────────────────
i18n:
  en:
    {key}: English text
    {key}: "Text with {{variable}}"
  de:
    {key}: German text
    {key}: "Text mit {{variable}}"
```

## The Pipeline: Five Stages

### Stage 1 — Interpret (LLM)

**Input:** Plain English description from user
**Output:** Structured follow-up questions

The Claude Code skill reads project context:
- `preview.config.yaml` (project settings)
- `src/preview/components/screen.tsx` (component catalog)
- `src/preview/blocks/` (block catalog)
- Existing screens in `src/screens/` (convention matching)

Then generates 2-5 UI-specific follow-up questions based on what's missing:

| Missing Section | Follow-up Question |
|---|---|
| No states defined | "What states should this screen have? (loading, empty, populated, error?)" |
| List with no status field | "Do list items have a status? What values?" |
| No navigation defined | "What happens when the user taps Continue?" |
| List mentioned but no empty state | "What should the user see when the list is empty?" |
| No locale info | "Should I generate German translations or do you want to provide them?" |

Questions use `AskUserQuestion` with multiple-choice options when possible.

### Stage 2 — Spec (LLM)

**Input:** Plain English + follow-up answers
**Output:** `screen.yaml` written to screen folder

The skill generates the complete YAML spec. The user reviews it:
- `[Enter]` Accept — proceed to generation
- `[e]` Edit — open in editor, re-validate after save
- `[r]` Regenerate — re-run Stage 2 with additional instructions

**This is the only human checkpoint.** Everything after this is automated.

### Stage 3 — Contract (Deterministic)

**Input:** `screen.yaml`
**Output:** `scenarios.ts`, `flow.ts`, `types.ts`, `en.json`, `de.json`

Pure YAML-to-code transformation. No LLM. Every output line traces to a spec line.

#### Mapping: `data:` section to `types.ts`

| YAML Type | TypeScript Type | Mock Generator |
|-----------|----------------|----------------|
| `string` | `string` | `faker.lorem.word()` |
| `date` | `string` | `faker.date.recent().toISOString()` |
| `number` | `number` | `faker.number.int()` |
| `boolean` | `boolean` | `faker.datatype.boolean()` |
| `A \| B \| C` | `'A' \| 'B' \| 'C'` | Random pick from enum values |
| `list` | `T[]` | Generate `min_items` objects |
| `{field}?` | `field?: T` | 50% chance populated |

#### Contextual mock field heuristics

| Field Pattern | Mock Generator |
|---|---|
| `*name`, `*Name` | `faker.person.fullName()` |
| `*email` | `faker.internet.email()` |
| `*date`, `*Date`, `*Time` | `faker.date.recent()` |
| `*id`, `*Id` | `faker.string.uuid()` |
| `*price`, `*amount` | `faker.finance.amount()` |
| `*phone` | `faker.phone.number()` |
| `*address` | `faker.location.streetAddress()` |
| `*status` | Pick from enum values |
| `*description`, `*note` | `faker.lorem.sentence()` |
| `*specialty` | `faker.person.jobArea()` |
| `*location` | `faker.location.city()` |

#### Mapping: `regions:` to `scenarios.ts`

Direct 1:1 mapping. `$mock` references are replaced with the generated mock data constant name.

#### Mapping: `actions:` to `flow.ts`

Direct 1:1 mapping. `$t(key)` references are resolved to the `en` locale value (flow triggers use display text).

#### Mapping: `i18n:` to `en.json` + `de.json`

Verbatim copy. No transformation.

### Stage 4 — Render (LLM)

**Input:** `screen.yaml` (elements section) + `scenarios.ts` (type contract) + component catalog
**Output:** `index.tsx` + `{screen}.spec.ts`

The LLM generates the React component, but is **heavily constrained**:

| Constraint | Enforced By |
|---|---|
| Must import exact type from `./scenarios` | Type system (tsc catches violations) |
| Can only use L2 components + L3 blocks | Skill prompt lists available components |
| Every `$t()` must match an i18n key | `verify-screen.sh` checks coverage |
| Every interactive element needs `data-flow-target` | `verify-screen.sh` checks triggers |
| Every `when()` must map to a region state | Type system (exhaustive checks) |
| Brand color tokens only | `verify-screen.sh` catches forbidden classes |

The `.spec.ts` file is **template-generated** (deterministic), not LLM-generated:
- One test per region x state combination
- Pattern: select screen, switch state, assert frame not empty

### Stage 5 — Verify (Deterministic)

Three sequential checks:

```
1. tsc --noEmit               → type errors in generated code
2. verify-screen.sh {screen}  → i18n gaps, forbidden colors, missing triggers
3. playwright test {screen}/  → runtime rendering errors, console.error
```

**Retry logic:**
- On failure: feed error output back to Stage 4 LLM with instruction "fix the code to match the spec"
- Max 3 retries per check
- If all retries exhausted: surface errors to user with the spec as reference

## CLI Commands

### `npx preview-tool init`

Scaffolds the preview system into any React+Vite repo.

**Steps:**
1. Detect tech stack (React version, bundler, CSS, package manager)
2. Create `preview.config.yaml` with detected defaults
3. Copy L1 tokens, L2 components, L3 blocks into `src/preview/`
4. Install `@preview-tool/devtools` as devDependency
5. Add `preview:dev` script to `package.json`
6. Install Claude Code skill at `.claude/skills/preview/SKILL.md`

**`preview.config.yaml`:**
```yaml
screens_dir: src/screens
components: src/preview/components/screen.tsx
tokens: src/preview/tokens/index.ts
blocks_dir: src/preview/blocks
locales: [de, en]
default_locale: de
brand:
  primary: teal
  accent: coral
  surface: cream
  text: charcoal
  muted: slate
```

### `npx preview-tool add`

The main pipeline. Runs Stages 1-5 in sequence.

**Interactive flow:**
```
$ npx preview-tool add

  Describe your screen (plain English):
  > A list of patient appointments showing doctor, date, status.
  > User can search by doctor name. Tapping opens detail.

  Analyzing...

  Follow-up questions:
  1. What states should the list have?
     [x] Loading  [x] Empty  [x] Populated
  2. Section name?
     > booking
  3. Navigation target for detail?
     > /booking/appointment-detail

  Generating spec...
  Review: src/screens/booking/appointments/screen.yaml
  [Enter] Accept  [e] Edit  [r] Regenerate

  Generating artifacts...
    ✓ scenarios.ts
    ✓ flow.ts
    ✓ types.ts
    ✓ en.json + de.json
    ✓ index.tsx
    ✓ appointments.spec.ts

  Verifying...
    ✓ tsc --noEmit
```

### Vite Plugin

The main technical challenge: `import.meta.glob` is compile-time. The plugin solves this with virtual modules:

```typescript
// @preview-tool/devtools/vite-plugin.ts
export function previewToolPlugin(options: { screensDir: string }) {
  return {
    name: 'preview-tool',
    resolveId(id: string) {
      if (id === 'virtual:preview-screens') return id
      if (id === 'virtual:preview-flows') return id
      if (id === 'virtual:preview-locales') return id
    },
    load(id: string) {
      if (id === 'virtual:preview-screens') {
        // Generate glob imports for consumer's screens directory
        return generateScreenGlobs(options.screensDir)
      }
      // ... similar for flows and locales
    },
  }
}
```

### Consumer Integration

## Differentiators vs Market

| Property | v0 / Bolt / Lovable | This Tool |
|----------|:---:|:---:|
| Dead buttons | Common | Impossible — every trigger in `actions:`, verified |
| Missing states | Happy path only | Impossible — states forced in Stage 1 |
| Untranslated strings | Common | Impossible — i18n in spec, verified |
| Hallucinated components | Common | Impossible — constrained to L2+L3 catalog |
| Wrong colors / styling | Common | Impossible — brand tokens verified |
| No typed API contract | Universal | `types.ts` exported for backend teams |
| No tests | Universal | `.spec.ts` auto-generated, one per state |
| Architectural chaos | Common | Impossible — layer dependencies enforced |
| Setup time | Minutes | `npx preview-tool init` — one command |
| Time to first screen | Varies | < 5 minutes (spec review is the bottleneck) |

## Build Phases

| Phase | Scope | Depends On | Parallel? |
|-------|-------|-----------|:---------:|
| **P1: Parser** | Deterministic `screen.yaml` → `scenarios.ts`, `flow.ts`, `types.ts`, locales | Nothing | Yes |
| **P2: Skill (Interpret + Spec)** | Claude Code skill for Stages 1-2 | P1 (validates spec) | — |
| **P3: Skill (Render)** | Claude Code skill for Stage 4 (index.tsx generation) | P1 (needs contract files) | — |
| **P4: Devtools Package** | Extract `@preview-tool/devtools` + Vite plugin | Nothing | Yes (with P1) |
| **P5: CLI Wrapper** | `init`, `add`, `dev`, `export` commands | P1, P2, P3, P4 | — |
| **P6: Verify Loop** | Stage 5 retry logic | P1, P3 | — |

**P1 and P4 can build in parallel.** P2 and P3 depend on P1. P5 integrates everything. P6 wraps the verification loop.

## Risks & Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| YAML indentation errors by PMs | Spec parsing fails | Tool generates YAML (PM reviews, not writes); linter on save |
| LLM generates wrong component in Stage 4 | Broken screen | Stage 5 catches type errors; retry loop fixes automatically |
| Vite plugin complexity | Hard to maintain | Plugin is thin (~100 LOC); only rewrites glob imports |
| `@faker-js/faker` bundle size | Slow init | Faker only used at generation time (CLI), not in runtime bundle |
| Screen patterns not covered by L2+L3 | User blocked | `preview.config.yaml` supports extending component catalog |
| Claude Code not installed | CLI unusable for Stages 1-2, 4 | Graceful fallback: skip LLM stages, user writes screen.yaml + index.tsx manually; Stage 3 still works |

## Open Questions

1. **Should `screen.yaml` support multi-region screens?** Current design supports it via multiple entries under `regions:`. Need to validate the parser handles cross-region state references.

2. **Should `init` detect existing design systems?** If the repo already has shadcn components, should the tool use those instead of shipping its own L2? Adds complexity but improves adoption.

3. **How to handle screen updates?** When a PM edits `screen.yaml` after initial generation, should `npx preview-tool regenerate` re-run Stages 3-5? Need to preserve manual edits to `index.tsx`.

4. **Should the tool support custom blocks?** If a screen needs a pattern not covered by DataTable/DataList, should the `add` command prompt the user to create a new block first?

5. **What's the minimum viable `screen.yaml` schema?** Can we infer more from less? E.g., if a list field exists in `data:`, auto-generate loading/empty/populated states without explicit `regions:` definition.
